================================================================================
  2. PHASE 1 — DATA ENGINEERING & BASELINE MODEL (5 CLASSES)
================================================================================

GOAL
────
  Prove the full pipeline end-to-end on a 5-class subset before committing to
  the full 101-class training run. Target: >85% top-1 accuracy on validation.

DURATION ESTIMATE (on RTX 4050)
────────────────────────────────
  Download Food-101     : 15-30 min (one-time, ~5 GB)
  Split + verify        : 5 min
  Training 20 epochs    : ~1.5-2 hours
  Evaluation + charts   : 10 min

STEP 1 — Install Python Environment
─────────────────────────────────────
  1. Install Python 3.11 (NOT 3.12 — some torch extensions lag behind).
     Download from python.org, check "Add to PATH".

  2. Install CUDA Toolkit 12.1 (matches PyTorch 2.x stable):
     https://developer.nvidia.com/cuda-12-1-0-download-archive
     Select: Windows → x86_64 → 11 → exe (local)

  3. Create a virtual environment INSIDE food_recognition/:
       cd meal_planning_app/food_recognition
       python -m venv venv
       venv\Scripts\activate          (Git Bash: source venv/Scripts/activate)

  4. Install dependencies (see requirements.txt in Section 9):
       pip install torch torchvision --index-url https://download.pytorch.org/whl/cu121
       pip install -r requirements.txt

  5. Verify GPU is detected:
       python -c "import torch; print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0))"
     Expected output:
       True
       NVIDIA GeForce RTX 4050 Laptop GPU

STEP 2 — Download Food-101 Dataset
────────────────────────────────────
  Create data/download_food101.py:

  ┌──────────────────────────────────────────────────────────────────┐
  │ import torchvision.datasets as datasets                          │
  │ datasets.Food101(root='data/food-101', split='train',           │
  │                  download=True)                                  │
  │ datasets.Food101(root='data/food-101', split='test',            │
  │                  download=True)                                  │
  └──────────────────────────────────────────────────────────────────┘

  Run:  python data/download_food101.py

  IMPORTANT: Add data/food-101/ to .gitignore immediately.
  Add models/checkpoints/ to .gitignore immediately.

STEP 3 — Choose Your 5 Classes
────────────────────────────────
  Use this specific 5-class selection (chosen to test both easy and hard cases):

    1. pizza          → visually distinct, high-contrast, large training signal
    2. sushi          → visually distinct, fine-grained texture features
    3. ice_cream      → distinctive color/shape
    4. waffles        → grid texture, easy to confuse with pancakes
    5. pancakes       → similar to waffles — tests model discrimination

  WHY: classes 4 and 5 are intentionally similar. If your baseline can
  distinguish them, it validates your augmentation and feature learning.

STEP 4 — Implement the Dataset Class (train/dataset.py)
─────────────────────────────────────────────────────────
  Your Dataset class must:
    - Accept a list of (image_path, class_index) tuples
    - Apply different transforms for train vs val (no augmentation on val)
    - Normalize with ImageNet stats: mean=[0.485, 0.456, 0.406],
                                     std=[0.229, 0.224, 0.225]

  Train transforms (in order):
    1. RandomResizedCrop(224, scale=(0.7, 1.0))   ← simulates zoom/crop
    2. RandomHorizontalFlip(p=0.5)
    3. RandomVerticalFlip(p=0.2)                  ← less common but helps
    4. RandomRotation(degrees=15)
    5. ColorJitter(brightness=0.3, contrast=0.3, saturation=0.2)
    6. ToTensor()
    7. Normalize(mean, std)

  Val/Test transforms (in order):
    1. Resize(256)
    2. CenterCrop(224)
    3. ToTensor()
    4. Normalize(mean, std)

STEP 5 — Stratified Train/Val Split from Official Split
─────────────────────────────────────────────────────────
  Food-101 ships train.txt (750 images/class) and test.txt (250/class).
  DO NOT touch test.txt during training. Instead:

    - From the official train.txt (750 per class × 5 = 3,750 images):
        Train : 600 per class (80%) = 3,000 images
        Val   :  150 per class (20%) =   750 images
    - Use sklearn.model_selection.StratifiedShuffleSplit to split.
    - Set random_state=42 for reproducibility.

  This preserves Food-101 benchmark comparability because the test split
  (250 per class from test.txt) remains the official held-out set.

STEP 6 — Build Baseline Model (models/baseline_resnet18.py)
─────────────────────────────────────────────────────────────
  Architecture:
    - Load ResNet-18 with ImageNet pretrained weights
    - FREEZE all convolutional layers
    - Replace the final fc layer with: Linear(512, num_classes=5)
    - Only train the new classification head for epochs 1–5
    - UNFREEZE layer4 (the last residual block) for epochs 6–20 with LR × 0.1

  Loss function : CrossEntropyLoss (no label smoothing yet — that is Phase 2)
  Optimizer     : Adam(lr=1e-3) for head, Adam(lr=1e-4) for unfrozen layers
  Scheduler     : ReduceLROnPlateau(patience=3, factor=0.5)
  Batch size    : 32
  Epochs        : 20
  Early stopping: halt if val_loss does not improve for 5 consecutive epochs

STEP 7 — Training Script (train/train_phase1.py)
──────────────────────────────────────────────────
  The training loop must write results to the result folders after EACH epoch.

  After each epoch, write two files:
    training_result/epoch_{N:03d}.json
    validatation_result/epoch_{N:03d}.json

  After training completes, save the best checkpoint:
    models/checkpoints/phase1_best.pth
    (save when val_accuracy improves — track best_val_acc)

================================================================================
  3. PHASE 2 — FULL-SCALE TRAINING (101 CLASSES)
================================================================================

GOAL
────
  Scale to all 101 Food-101 classes using ResNet-50 (primary) and MobileNetV2
  (secondary, for mobile deployment). Target: >80% top-1 accuracy on the
  official test set (matching published ResNet-50 benchmarks).

DURATION ESTIMATE (on RTX 4050, RTX 4050 = ~6 GB VRAM)
─────────────────────────────────────────────────────────
  Full dataset split  : 10 min
  ResNet-50 training  : ~30-40 min/epoch × 30-50 epochs = 15-33 hours total
  MobileNetV2 training: ~15-20 min/epoch × 30 epochs = 7-10 hours total

  STRATEGY: Run overnight. Use a training script that saves checkpoints every
  5 epochs so you never lose more than 5 epochs of work.

  ALTERNATIVE if you want faster iteration: Use Google Colab Pro ($10/month)
  with an A100 GPU — reduces ResNet-50 epoch time to ~4-5 minutes.
  But your RTX 4050 is sufficient; just start training before sleeping.

STEP 1 — Full Stratified Split (101 classes)
──────────────────────────────────────────────
  Same logic as Phase 1 but across all 101 classes:
    From official train.txt (750 × 101 = 75,750 images):
      Train : 600/class (80%) = 60,600 images
      Val   : 150/class (20%) = 15,150 images
    Test  : official test.txt (250 × 101 = 25,250 images) — untouched

STEP 2 — ResNet-50 Architecture
─────────────────────────────────
  Architecture:
    - Load ResNet-50 with ImageNet pretrained weights
    - FREEZE all layers
    - Replace fc with: Linear(2048 → 512) → ReLU → Dropout(0.4) →
                       Linear(512 → 101)
    - Training strategy (discriminative fine-tuning in 3 stages):

    Stage A (Epochs 1–10):
      Freeze entire convolutional base.
      Train classification head only.
      LR = 1e-3, batch = 32.

    Stage B (Epochs 11–25):
      Unfreeze layer4 (last residual block).
      Train head + layer4.
      LR_head = 1e-3, LR_layer4 = 1e-4.

    Stage C (Epochs 26–50):
      Unfreeze layer3 + layer4.
      LR_head = 1e-3, LR_layer3 = 5e-5, LR_layer4 = 1e-4.
      Introduce Label Smoothing: CrossEntropyLoss(label_smoothing=0.1)

  Scheduler: CosineAnnealingLR (T_max = epochs per stage, eta_min = 1e-6)
  Gradient clipping: max_norm=1.0 (prevents gradient explosion during unfreeze)
  Mixed precision: torch.cuda.amp.autocast() — saves ~40% VRAM, 30% faster

STEP 3 — MobileNetV2 Architecture (mobile deployment target)
──────────────────────────────────────────────────────────────
  Architecture:
    - Load MobileNetV2 with ImageNet pretrained weights
    - Replace classifier with: Dropout(0.2) → Linear(1280 → 101)
    - Unfreeze all layers from epoch 1 (MobileNetV2 is already lightweight)
    - LR = 5e-4, batch = 64, epochs = 30
    - Use same label smoothing + cosine schedule as ResNet-50 Stage C

  Why train both?
    ResNet-50 → for server-side API inference (Railway deployment)
    MobileNetV2 → potentially for on-device inference in the React Native app
                  via react-native-fast-pytorch or TFLite conversion

STEP 4 — Checkpoint Strategy
──────────────────────────────
  Save checkpoints:
    models/checkpoints/phase2_resnet50_epoch_{N:03d}.pth  (every 5 epochs)
    models/checkpoints/phase2_resnet50_best.pth            (best val accuracy)
    models/checkpoints/phase2_mobilenetv2_best.pth

  Checkpoint file contains:
    {
      "epoch": N,
      "model_state_dict": ...,
      "optimizer_state_dict": ...,
      "val_accuracy": 0.8123,
      "val_loss": 0.6234,
      "config": { "architecture": "resnet50", "num_classes": 101 }
    }

  Why save optimizer state? Allows resuming training from exact same optimizer
  momentum state if your laptop loses power or you need to pause.

  Resume command:  python train/train_phase2.py --resume models/checkpoints/phase2_resnet50_epoch_025.pth

STEP 5 — Out-of-Distribution (OOD) Detection
──────────────────────────────────────────────
  After full training, calibrate the confidence threshold:

  Method: Softmax thresholding (simplest, production-proven)
    - Run the trained model on 500 non-food images (download ImageNet subset of
      "vehicles", "animals", "furniture" — ~100 images each)
    - Find the threshold T where:
        True Rejection Rate (non-food correctly rejected) > 95%
        False Rejection Rate (real food incorrectly rejected) < 5%
    - Expected T ≈ 0.65–0.80 based on the PDF recommendation of 0.75

  Save calibrated threshold to:
    models/ood_threshold.json: { "threshold": 0.72, "calibrated_on": "500 non-food images" }

  In production (api/ood_detector.py):
    If max(softmax_output) < threshold:
      Return {"status": "unknown", "message": "Image not recognized as food.
              Please select manually.", "top5_candidates": [...]}

================================================================================
  4. PHASE 3 — FASTAPI MODEL SERVING LAYER
================================================================================

GOAL
────
  Expose the trained model as a REST API endpoint that the existing
  Node.js backend (Railway) can call. Mirror the structure of the existing
  Flask app in machine_learning/ but use FastAPI for async performance.

ARCHITECTURE
────────────
  React Native App
       │  POST /upload-image (base64 or multipart/form-data)
       ▼
  Node.js Backend (Railway)         ← existing service, no changes needed
       │  POST /api/food-recognition/predict
       ▼
  FastAPI Food Recognition Service  ← NEW — food_recognition/api/main.py
       │  1. Decode & preprocess image
       │  2. Run CNN forward pass → top-5 predictions + confidence scores
       │  3. OOD check (reject if max_softmax < threshold)
       │  4. Call FatSecret foods.search.v3 with predicted label
       │  5. Call FatSecret food.get.v4 with confirmed food_id
       ▼
  Return nutritional JSON to backend → backend returns to app

STEP 1 — FastAPI App (api/main.py)
────────────────────────────────────
  Endpoints:
    POST /predict
      Input : multipart image file OR base64 encoded JPEG/PNG (max 10 MB)
      Output: {
        "status": "success" | "unknown" | "error",
        "prediction": {
          "label": "pizza",
          "confidence": 0.9234,
          "top5": [
            {"label": "pizza",     "confidence": 0.9234},
            {"label": "calzone",   "confidence": 0.0412},
            {"label": "flatbread", "confidence": 0.0198},
            ...
          ]
        },
        "nutrition": {
          "food_id": "33691",
          "food_name": "Pizza",
          "calories": 266,
          "protein": 11.0,
          "carbohydrates": 33.0,
          "fat": 10.0
        }
      }

    GET /health
      Output: { "status": "ok", "model_loaded": true, "model_version": "phase2_resnet50" }

    GET /classes
      Output: { "classes": ["apple_pie", "baby_back_ribs", ...] }  ← all 101 class names

STEP 2 — Predictor Class (api/predictor.py)
────────────────────────────────────────────
  - Load model ONCE at startup using FastAPI lifespan events (not on every request)
  - Cache model in memory — do not reload per request
  - Use torch.inference_mode() for all forward passes (faster than no_grad)
  - Target inference time: < 300ms on CPU (Railway has no GPU)

  CPU inference note:
    ResNet-50 on CPU takes ~150-400ms per image.
    MobileNetV2 on CPU takes ~50-150ms per image.
    RECOMMENDATION: Deploy MobileNetV2 on Railway for latency, keep ResNet-50
    as local/research model. Or convert ResNet-50 to ONNX (see Section 5).

STEP 3 — FatSecret Integration
────────────────────────────────
  Reuse the existing OAuth 2.0 logic from:
    machine_learning/recommendation_engine/fatsecret.py

  Do NOT rewrite it. Copy the relevant search/get functions into:
    api/fatsecret_client.py

  Call order:
    1. foods.search.v3(q=predicted_label, max_results=5)
    2. Select best food_id (prefer generic items over branded)
    3. food.get.v4(food_id=selected_id)
    4. Return macros: calories, protein, carbs, fat

  Cache results in a local dict for 24 hours (per FatSecret ToS):
    cache key = label string
    cache value = { "food_id": ..., "nutrition": {...}, "cached_at": timestamp }
    Invalidate if cached_at > 24 hours old

STEP 4 — Dockerfile (api/Dockerfile)
──────────────────────────────────────
  FROM python:3.11-slim

  WORKDIR /app

  COPY requirements.txt .
  RUN pip install --no-cache-dir -r requirements.txt

  COPY models/checkpoints/phase2_mobilenetv2_best.pth ./models/
  COPY models/food101_classes.json ./models/
  COPY models/ood_threshold.json ./models/
  COPY api/ ./api/

  EXPOSE 8000
  CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]

  IMPORTANT: The Docker image will be ~1.5–2 GB due to PyTorch CPU wheels.
  Use python:3.11-slim (not full) and install torch CPU-only:
    pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu

PHASE 3 SUCCESS CRITERIA
─────────────────────────
  ✓ POST /predict returns correct label for 10 manual test images
  ✓ OOD path returns "unknown" for a photo of a car
  ✓ /health endpoint returns 200 OK
  ✓ Docker image builds successfully (docker build -t food-recognition .)

  5. PHASE 4 — DEPLOYMENT STRATEGY & SERVICE RECOMMENDATIONS
================================================================================

THE CORE PROBLEM
────────────────
  Railway Hobby Plan ($5 credit/month) gives each service:
    - Up to 8 GB RAM (shared across all services)
    - 100 GB outbound bandwidth
    - No GPU

  A PyTorch CPU container (FastAPI + MobileNetV2) requires:
    - ~1.0–1.5 GB RAM (model in memory + FastAPI workers)
    - This is feasible on Railway, but leaves little headroom if your
      recommendation ML service also runs on the same plan

DEPLOYMENT OPTIONS — RANKED BY FIT FOR YOUR STACK
───────────────────────────────────────────────────

  ★★★★★  OPTION A — Railway (new service, same project) [RECOMMENDED]
  ────────────────────────────────────────────────────────────────────
    Deploy the FastAPI food recognition container as a 3rd Railway service
    alongside your existing backend and ML recommendation service.

    Pros:
      - Everything in one place (one dashboard, one billing)
      - Automatic HTTPS, custom domains
      - GitHub Actions CI/CD integration
      - No new accounts or services to manage
      - $5/month covers it if your usage is moderate

    Cons:
      - No GPU (CPU inference only — use MobileNetV2 to stay fast)
      - All 3 services share the $5 credit pool

    Deploy steps:
      1. Push food_recognition/api/ + Dockerfile to GitHub
      2. Create new Railway service → "Deploy from GitHub"
      3. Set build context to food_recognition/
      4. Set environment variables: FATSECRET_KEY, FATSECRET_SECRET
      5. Railway auto-assigns a public URL: food-recognition.up.railway.app
      6. Update backend to call this URL for /predict

  ★★★★☆  OPTION B — Hugging Face Spaces (Free Tier)
  ──────────────────────────────────────────────────
    HF Spaces hosts ML model demos/APIs for free using Gradio or FastAPI.

    Pros:
      - Free (zero cost — no impact on Railway budget)
      - Built for PyTorch models, first-class support
      - 16 GB RAM on free CPU tier (more than Railway)
      - Can upgrade to GPU ($0.60/hour T4) on-demand

    Cons:

      - Slightly more complex deployment (HF-specific config)

  ──────────────────────────────────────────────────────
    A general-purpose EC2 instance with 2 vCPUs, 4 GB RAM.

    Pros:
      - Predictable performance, no cold starts
      - Full control over environment
      - Can attach persistent EBS volume for model storage

    Cons:
      - ~$30–40/month (most expensive option here)
      - Requires manual server management (nginx, SSL, etc.)
      - Overkill for your current scale

    RECOMMENDATION: Skip for now. Revisit if you outgrow Railway.

  ★★★☆☆  OPTION D — AWS Lambda + API Gateway (Serverless)
  ──────────────────────────────────────────────────────────
    Event-driven serverless — pay only per invocation.

    Pros:
      - ~$0 at low traffic (first 1M requests/month free)
      - No server management

    Cons:
      - Lambda has 250 MB code size limit (PyTorch alone is ~800 MB) →
        must use Lambda container images (more complex)
      - 3–8 second cold starts on infrequent use (catastrophic for UX)
      - 15 minute max execution time (fine for inference)

    RECOMMENDATION: Not suitable for this use case due to cold starts and
    PyTorch container image complexity.

  ★★★☆☆  OPTION E — Google Cloud Run (Serverless containers)
  ─────────────────────────────────────────────────────────────
    Similar to Lambda but with Docker containers and better cold start.

    Pros:
      - Pay per request
      - $0 for first 2M requests/month (free tier)
      - 4 GB RAM per container instance

    Cons:
      - Cold start: ~2–5 seconds for a PyTorch container
      - More complex than Railway (need Google Cloud account, gcr.io registry)

    RECOMMENDATION: Good secondary option if Railway Hobby plan becomes too
    expensive. Use minimum-instances=1 to eliminate cold starts (~$5/month).

================================================================================
  10. DECISION LOG (Why We Chose X Over Y)
================================================================================

  ResNet-50 over VGG-19
    VGG-19 is larger (~550 MB) with more parameters but similar accuracy.
    ResNet-50 (~100 MB) is faster, trains faster, and deploys cheaper.

  MobileNetV2 for deployment over ResNet-50
    ResNet-50 CPU inference: ~200-400ms. MobileNetV2 CPU inference: ~50-150ms.
    Railway has no GPU — latency matters. MobileNetV2 accuracy is comparable
    on Food-101 and half the memory footprint.

  ONNX over raw PyTorch for API serving
    ONNX Runtime CPU inference is 2-4x faster than PyTorch CPU inference
    with no accuracy loss. Worth the 10-minute export step.

  Railway over AWS EC2 for model serving
    Railway is already your platform. Adding a 3rd service costs zero extra
    setup time. EC2 would cost $30+/month and require nginx/SSL setup manually.
    Revisit when monthly active users exceed ~5,000.

  Official Food-101 test split preserved
    Using the official test.txt unchanged makes your accuracy numbers directly
    comparable to published papers (e.g., ResNet-50 ~80% top-1, MobileNetV2 ~83%).
    A custom split would make your numbers unverifiable against benchmarks.

  Local RTX 4050 over Google Colab for training
    You have a CUDA-capable GPU available at zero marginal cost.
    Colab disconnects after 12 hours of inactivity. Local training with
    checkpoints is more reliable for 15–33 hour training runs.
    Use Colab only as a backup.
